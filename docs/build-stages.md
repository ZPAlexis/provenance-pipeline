# Build stages

[← README](../README.md)

The entries name the operator's AI assistant as it was used then: Claude, through Claude Desktop. Any MCP client should work; only Claude Desktop has been tested so far.

**Stage 1 — Job Finder** ✅ A thin vertical slice through the whole stack rather than a horizontal layer, so something useful ships before the CRUD work and the governance model is proven on real data early.

- **1.1 — Schema and ingest** ✅
- **1.2 — Verification agent** ✅ (Playwright + LLM, Python worker; see [`workers/verifier`](../workers/verifier)), in three slices:
  - **1.2a — Render and extract** ✅ read a careers page in a real browser and extract its listings; known job boards (Greenhouse, Lever, Ashby, Workday, Oracle Cloud) are read through their APIs instead.
  - **1.2b — Resolve careers pages** ✅ find each company's careers page from its domain, cheapest step first, with a confidence; low-confidence finds wait for a person. Measured by hiding the known pages of 71 labelled companies and finding them again: 87% found, none wrong at high or medium confidence.
  - **1.2c — Match and verdict** ✅ read each watched page in full (pagination, "load more", ATS APIs), match every tracked posting against it, and record verdicts that follow the evidence. Measured on fresh reads of 59 roles with research labels: 58 called right, 54 as labelled and 4 where hand checks showed the label wrong; the one miss was a live role left as couldn't confirm. No closed role was reported open, and every role it reported closed was (12 of 12).
  - **Cost pass** ✅ a check pays the LLM to read a page only when its role links changed or its last full read is more than 14 days old, and a company's own free ATS board is read in place of its page when it lists the same roles.
- **1.3 — Scoped writes and provenance** ✅ a credential per agent run with exactly that run's scopes, checked at every write down to the attributes it sets; refused writes audited; every agent write names its credential; an Agents page and `agents:` commands. See [The permission model](governance.md).
- **1.4 — Monitoring on demand, and what changed** ✅ one role, one company, or everything, checked when the operator asks: "Check everything" on the dashboard (since 4e, "Check all tracked companies" on the Roles page) shows its plan and ceiling and asks first, then runs in the background with its progress (137 companies in 47 minutes for $1.17, the first time). A what-changed view (since 4e, the audit log's Check results) reports what each check of everything found: verdicts, suggestions made and withdrawn, careers pages, boards, new review questions, refused writes, and lists that changed a lot between whole reads (raised for review: often another page now). A schedule comes with Stage 4.
- **1.5 — Capture and watched roles** ✅ the first web UI. A search profile suggests roles from the watched pages, the user picks which to track, and each tracked role gets a "check now" that answers *still listed* or *no longer listed*. Paste a careers link, a posting link, or a company domain to resolve, verify, and add it to the watch list. In five slices:
  - **1.5a — Tracked roles and check now** ✅ a tracking state only the operator sets; each role's own page at the employer, matched before its title; `verifier:check`, the role's own page first, then its company's careers page.
  - **1.5b — The operator's pages** ✅ dashboard, roles, companies; track, archive ("dismiss", as it was then called), and check now from them.
  - **1.5c — The search profile and suggestions** ✅ a profile edited on its own page; the worker weighs every watched page's latest roles against it at no cost, and an agent of its own suggests the ones that fit, each with why, never one already on record. Refreshed when the profile is saved, on demand, and after every check.
  - **1.5d — Add by URL** ✅ a company by its domain, careers page, or ATS board, and a role by its own page, from the Companies and Roles pages: never added twice, read right away (its careers page found first), what that could cost asked first. A role's title is optional: its page names it. A careers page found at low confidence is confirmed, rejected, or set right on the company's page.
  - **1.5e — The review queue** ✅ what the agents can't settle, raised by them with what was seen and an action proposed: careers pages found at low confidence, suggested kinds, companies with no careers page found, lists read only in part, answers resting on the AI's judgment alone or on a read that saw no roles, and roles that couldn't be confirmed. Decided from the Review page or `review:decide`, through the same audited services as everywhere else.

**Build order was 1.2 → 1.5 → 1.3 → 1.4.** Capture needs only 1.2, so it shipped first to make the tool usable early; 1.3's check sits where every write passes, at the model layer, so it covered capture, suggestions and the review queue without reworking them. Monitoring is human-triggered first, so nothing waits on a host or a scheduler.

**Stage 2 — Pipeline system** ✅ Applications/activities/drafts, CRUD and review UI, MCP server exposing scoped tools, additional agents. In slices:

- **2a — Applications** ✅ one per role, started from its page (tracking it if it wasn't), moved through Interested, Applied, Screening, Interviewing, Offer and Accepted (since 4e: Interested, Preparing, Applied, Interviewing, Offer, Accepted), or closed as Rejected, Withdrawn or No response, by the operator alone, each change dated and noted; what happened along the way logged; a pipeline page by stage, and `applications:` commands.
- **2b — Descriptions and the resume** ✅ each role's description read from its own page (through its board's job API, or the page rendered; never the LLM), when an application starts or when asked, kept as versions, a change shown in what changed; the operator's resume pasted on the Profile page, kept as versions in the database only.
- **2c — The draft agent** ✅ a cover letter or an outreach note for an application, written by Opus 5.5 from the resume, the role's description, the profile and the operator's notes, in the description's language unless another is asked: it claims only what the resume shows, cites the resume lines it drew on, and lists what the role asks that the resume doesn't show. Written in the background from the application's page, where the operator edits, approves and copies it; nothing is ever sent. `drafts:` commands.
- **2d — Writing through MCP** ✅ an MCP server (grown from the author's first MCP server and client, built from raw JSON-RPC) through which the operator's own AI assistant, on their subscription rather than API credits, reads an application's materials and the shared writing rules, writes a resume review, a cover letter, an outreach note or a tailored resume, and saves it back as `agent:assistant` under a credential per call, read against the resume version it saw. The resume review also runs in the app, written by the drafter. `reviews:` commands.
- **2e — Contacts and the activity logger** ✅ the people the operator deals with at each company (recruiters, hiring managers, referrers, interviewers), kept with the company and linked to its applications, on both pages; an activity names whom it was with, and an outreach note, from the drafter or the client, can be addressed to one, opening with their first name. Through MCP the client adds and updates contacts and logs what the operator tells it, never moving a stage. `contacts:` commands.
- **2f — Fit scoring** ✅ each role weighed against the resume from its own description, by Haiku 4.5: a score from 0 to 100, the level the role asks, the strongest matches by resume line, the gaps, and why; only when asked, a batch with its cost shown first. On a role's page, and on the Roles page as a Fit column to filter and sort by, with the unscored weighed in the background from there. `fit:` commands. Or from the operator's own AI assistant through MCP, on their subscription: it finds roles on the watched pages by meaning, rather than the profile's exact words, suggests the ones that may fit, has their descriptions read, and weighs each by the same rules.
- **2g — The review agent** ✅ the operator's own AI assistant, through MCP, recommends a decision on each open review item (one of its own actions, with what it checked and why) and never decides one; the operator accepts or decides otherwise, and agreement is measured per kind. Recommendations sit on their items on the Review page with a one-click Accept, and agreement shows there and on the Agents page; MCP tools and a prompt to work through the queue; `review:accept` and `review:agreement`. No kind acts on its own: autonomy, if ever, is earned per kind on measured agreement.

**Stage 3 — Governance completion** ✅ (decided 2026-10-28, complete 2026-10-29). The record made answerable, and read-only throughout: no new agent, scope or kind of write. Each part is read on a page, by a command and through an MCP read tool.

- **3.1 — The audit log, searchable** ✅ every write on record on one page, newest first, narrowed by who made it (the operator, every agent, or one), the kind of record, the action (created, changed, deleted, refused), a date range, one record or the credential behind it, and an attribute it changed; each event with what it changed, why, and its credential. The pages that show history link to it, already narrowed. The same from the command line (`audit:list`), and through MCP (`query_audit_log`), so the operator's client can answer who did what and why.
- **3.2 — A review queue for drafts** ✅ met by 2c and 2g: nothing an agent writes takes effect until the operator approves a draft or accepts a recommendation.
- **3.3 — Analytics** ✅ in raw SQL over the audit log and the evidence, every input a bound parameter, on an Analytics page (since 4e, the dashboard's tabs). The pipeline so far: how far applications get (each counted at every stage up to its furthest) and the rate from one stage to the next; the days in each stage, from the operator's own stage dates (a move made the same day as the stage before carries that date forward; an application still at a stage counts its days so far); how they end (accepted of those closed, an offer of those applied); and what is open now, beside the tracked roles still listed with no application. The watch: how long roles stay listed (first seen listed to first seen gone, by the checks' own days), the roles the reads matched and the answers that changed week by week, and how fresh the tracked roles' answers are. The agents: what the AI cost by day (with a running total), purpose and model, a verification read and a role confirmed listed (a read through a board's API needs no AI and still counts); the review queue's agreement per kind; and what each actor wrote and was refused, beside the credentials issued. A rate needs at least 5 to go on; below that the page says so. The same from the command line (`analytics:report`) and through MCP (`get_analytics`), a section at a time and for a period.

**Review pass** ✅ (2026-11-02 to 11-03). A full review of the project after Stage 3, closed step by step: the dependencies brought up to date (the AI SDK's major version among them); every MCP tool's record text fenced as data; private text kept out of the logs; the audit log made append-only in the database itself (a trigger); no page view that writes; the docs; specs for the commands; and every company on the private target list taken out of the repository and its history.

**Stage 4 — Showcase and distribution.** Last by design, so it ships a finished system, and nothing before it depends on it. As it went, it became a review of the experience from the operator's own use (4a to 4f); the showcase itself, a demo and a version to run locally, is Stage 5 (2026-11-26).

- **4a — Curating the watch list** ✅ (decided 2026-11-04, complete 2026-11-05). The first part of the review of the experience, from the operator's own use: a company tracked or archived as a role is, watched only while tracked; archiving one archives its roles in play, each on the record, and is refused while an application there is open; tracking it again brings them back. The Companies page has Tracked, Archived and All, with what needs a look (no careers page yet, a page to confirm, no role tracked, roles tracked none of which is still listed), each company's domain, careers page, roles (its tracked ones by answer) and application, and archives several at once; a company's page tracks or archives it, its careers page's details in a fold; review cards link the company's domain. "Archive" replaces "Dismiss" on the pages, the stored word unchanged. Adding reads nothing unless asked ("Add and check", "Add and read"), so it costs nothing: a role added so needs its title, a company can be given its careers page to be watched as given, and a role can be added from its company's page; a role's own page is changed from its page, never to a job board's link. The operator's own AI assistant does the same through [MCP](mcp.md) on their word (`watchlist:curate`, held by the assistant alone; "track or archive" is no longer the operator's alone), lists the companies as the page does, and adds a role tracked and never checked.
- **4b — Finding companies** ✅ (decided 2026-11-05, settled 2026-11-06, complete 2026-11-10). The operator's own AI assistant searches the open web for companies that fit preferences kept on the profile, researches each, and proposes it with a review; only the operator, or the client on their word, decides what is watched. A company the client proposes is held as `suggested`, with why, where it was found and what the app's own free read of its board saw, found on record as Add by URL finds it (refused when tracked or archived, refreshed when proposed already); nothing checks it, suggests its roles, asks about it or looks for its careers page until it is tracked, and tracking it reads its board at once, always free, the careers page still the verifier's write. The profile holds what the operator wants of a company (what they want and avoid, in their words, and the stages, sizes, business models, industries and words to avoid), audited by a hash where it is their own words, and saved by them or by their client on their word; a company review, the client's, scores a company from 0 to 100 against them, point by point with its sources, its facts in the preferences' own values, a company that does what they avoid capped at 49, stale when the preferences or the places change; the rules for it are shared ([`company_fit`](../workers/verifier/src/verifier/writing_rules.md#company_fit) in `writing_rules.md`). On the pages: the Profile page keeps the company preferences in a form of their own (saving them finds no role suggestions); the Companies page has a Suggested tab beside Tracked, Archived and All, where proposals are tracked or declined, one or several under one note, each with where it was found, what its board listed and why; every tab has a Fit column (the newest review's score, stale ones marked), sorted best first when asked, filtered by fit (85, 70 or 50 and up, not reviewed, stale) and by what the reviews found (stage, size, business model, an industry, a region); and a company's page shows its proposal and its company review in full, point by point with the sources, and the scores before it. Through [MCP](mcp.md) the client reads the preferences with the rules (and saves them on the operator's word), checks candidates against the record and their boards (free, recording nothing), proposes and reviews them, lists the companies by fit and what is due a review, and reads a company's proposal and review; the `find_companies` and `review_companies` prompts run the flow. A role's company fit (its company's newest review) shows beside the role's own fit on the Roles page, sortable by either, on a role's page, in `fit:list`, and through `find_roles` and `get_roles_to_weigh`; it is never weighed into a role's fit.
- **4c — Your background, and fit read two ways** ✅ (decided 2026-11-11, complete 2026-11-12). From the operator's own use: their client's fit reviews, on which most of their pruning rested, couldn't see the background that lives outside the resume and the company preferences. The profile gains a background in three parts, pasted (never a file), kept version by version, audited by each part's size and hash, and the operator's alone to edit. Each part is read only by what may use it: what they're looking for (motivation, for role fit and for cover letters and outreach notes, never a claim of experience), role preferences (role fit alone), and background not on the resume (role fit, and resume reviews and tailored resumes). Company reviews don't read it. A role's fit is read two ways: the ATS fit, the resume alone as a recruiter's screening system would read it, shown in the tables, and the Background fit beside it on a role's page, with the gaps the background covers (and where to address each, the resume or the cover letter) and how the role sits with each role preference. The background never raises the ATS fit; each reading goes stale on its own, and the roles weighed before the background are picked to weigh again, only when asked. A resume review or a tailored resume flags each point drawn from the background, "from your background, not on the resume", with its lines, for the operator to confirm; a cover letter or an outreach note takes only its motivation from it, so every claim still traces to a line of the resume, and one that cites a background line is refused. Every reading records the version of the part it read, and says when that part changed since. The same holds through [MCP](mcp.md), where each kind of writing is given only its part, and in the app's own agents, whose prompts changed on purpose: a smoke run on made-up records caught the fit scorer citing resume lines for role preferences only the background states, fixed before it shipped.

- **4d — Screen risk, and your links** ✅ (decided 2026-11-17, complete 2026-11-18). From an application turned down in two days, whose fit had read its minimum requirements as gaps but scored 74 (the rules let a minimum in years read as "a level one step off"). Before the score, each role's must-haves (what it states it requires: its minimum requirements, a number of years, a degree, where one must be based; never what it calls a bonus) are read one by one, each shown on the resume, only in the background, or not shown; a minimum stated in years is a must-have, never a level. One not on the resume caps the ATS fit at 69 and one shown nowhere the Background fit, applied by the app, not the model, the score as weighed kept beside it. A role's page names the screen risk above both readings ("Likely screened out on: …"), the Roles table marks it, and the roles weighed before the check are weighed again when asked. Then the operator's own links: up to five on the Profile page, their website and GitHub mattering most (LinkedIn refused: its pages can't be read, and what matters from it belongs in the background), read by the app, free and never by the AI (a GitHub account through its public API; any other site through its sitemap and the pages it links to on the same site, one level deep, robots.txt honored), only when saved or asked again, each page kept as a version. Each role is given the lines of those pages that share the most of its description's words, ranked by line (a rehearsal on the operator's own links found that a pick by page gave five roles the same three pages), and reads them as background not on the resume: the Background fit, and resume reviews and tailored resumes, each point drawn on them flagged "from your links"; never the ATS fit, a role preference, or a letter. The same holds through [MCP](mcp.md), where each role's lines come with a version its save is read back against, and in the app's own agents, whose prompts changed on purpose and were smoke-tested on made-up records.

- **4e — The first major review of the pages** ✅ (scoped 2026-11-11, decided 2026-11-23, complete 2026-11-26). From the operator's own use: eighteen points from two weeks of it, beside the 11-11 review of how the pages organize what they show, in ten steps; the operator's review of the whole app after them added three more. An interactive process, the tool in use throughout: another full review and smaller passes come after it.
  - **Step 1, tabs and one size of button:** one size for every button, a compact one only inside a table's rows; tabs inside a page, which load at once and switch instantly (a link to one of the page's anchors opens the tab holding it), first on the Profile page: Search profile, Resume, Background, Your links, and What you want of a company; and the record's own pages (the audit log, what changed, the analytics, the agents) in one menu in the top bar (step 13 made every page a tab of its own).
  - **Step 2, a role's page:** its listing, its three fits and its screen risk in the header beside Check now, Track or Archive and its application; its overview always in view; and tabs that open on its fit (the two fits first, then what the resume doesn't show, then what it shows), its description, and its checks and history, which now holds the fit scores saved for it, the AI assistant's included. "Listing" replaces "Answer" on the pages.
  - **Step 3, an application's page:** its stage, its role's listing and fits, its company's fit and its screen risk in the header, the stage path under it, and tabs: Activity (move it, log what happened, the timeline), Fit (the role's fit and the company's, so the work happens here), Writing (the newest resume review and the newest draft of each kind, the earlier ones folded), Contacts, Notes, and History, which holds what was saved under it: its activities, contacts, drafts and resume reviews, the AI assistant's included.
  - **Step 4, Preparing:** a stage before Applied, for researching the company and readying the resume and the application. Screening is gone: it came straight after applying and said nothing Interviewing doesn't, and no application ever stood at it. Each card on the Pipeline page shows the role's fit, marked when there is a screen risk, and its company's fit beside it.
  - **Step 5, the lists' order:** the Roles and Companies pages open in one order, what you are applying to first (the furthest along first), then what has no application, then what has a closed one, each by fit, then (companies) the roles tracked, then the last check; each list's tools in one row (its tabs, finding, adding), its filters and order as dropdowns under it, and the bar for acting on many shown only once one is picked. The Roles table shows each role's application, its company and place under its title, when it was checked in a few characters, and its own page as its site.
  - **Step 6, a company's page:** its tracking, fit, roles and open application in the header beside Check now and Track or Archive, its careers page in view, and tabs: Roles (first; a proposal opens on its Review), Review (its company review and how it was proposed), Careers page (how it was found, rename it, set it by hand, its recent checks), Contacts, and History, which holds its company reviews (the AI assistant's) and its contacts, a deleted one included.
  - **Step 7, a check of every tracked company:** "Check everything" became "Check all tracked companies", on the Roles page. Every tracked company's careers page is read again, a role on record or not (it used to read only those with one, so a tracked company with no role yet was never read and no new role there was ever suggested): the roles tracked confirmed and new ones that fit the profile suggested, its plan and the most it could cost asked first. The dashboard says how old the lists are, since the AI assistant's role search reads them as they were last read, and the search itself says so through [MCP](mcp.md). A check that moves a role's own page (to its posting on an ATS, say, from the careers page it was added from) has its description read again from the new page, free: what the page before said may describe another role, or none. Until it is, the role's page, its application's and what the AI assistant reads say so; each version of a description names the page it was read from.
  - **Step 8, adding a role by its link:** "Add by link" in the Roles page's toolbar (and on a company's page), the role's link alone, the rest under "More" (its title, where it was found, and the company's website, which an ATS link doesn't name). A link on an ATS board has the board watched at once, read free through its API; the role is checked right after when that is sure to cost nothing, and a check that could spend waits for Check now on its page, which says what it could cost. A careers-page link showing an ATS posting (`gh_jid`, `ashby_jid`) is added as that posting once the company's board is on record; until then its description isn't read from the careers page, and its first check finds the posting. A watched page on an ATS board is priced as free, read before or not.
  - **Step 9, the AI assistant's changes, said as they happen:** a role's, an application's or a company's page, while it is open, says when the AI assistant changes what it shows (its record, what was saved under it, and the fits in its header), in a note at the foot of the screen with Refresh, which reloads the page with its tab kept. The page asks every 20 seconds, as a check run's frame does while it runs, from the audit log alone: no live connection, nothing written, a few milliseconds an ask.
  - **Step 10, the record's pages and About:** the Agents page in tabs (who may write what, with what is yours alone first and each agent's scopes as chips, its full list in a fold; the credentials; the refused writes); Analytics in three tabs (the pipeline, the watch, the agents); What changed in tabs by what needs you first (new review questions, pages changed a lot), then listings, suggestions, pages and descriptions, and refused writes; the dashboard on about one screen (steps 11 and 12 then folded What changed into the audit log and Analytics into the dashboard); and the About page in four steps (watch, find, apply, govern) with a section for each and for the AI assistant. Every page now calls the operator's own client "your AI assistant", as the README does.
  - **Step 11, Check results in the audit log:** What changed is now the audit log's Check results tab (its page gone, its address leading there), one table of what a check of all tracked companies found, newest first, by kind, with what needs the operator marked (an open review question, a page that changed a lot) and the two kinds read from pages rather than written (descriptions, pages changed a lot) said so. Who wrote something is a colored badge everywhere it shows (you blue, your AI assistant purple, the app's agents teal, the system grey), and the record pages' filters look and apply as the lists' do, as soon as one changes.
  - **Step 12, the dashboard and Analytics in one page:** the dashboard, in three tabs (the pipeline, the watch, the agents), each with what stands now in full-size tiles on top and how it has gone under them, since a day if set; the stage tiles carry each stage's median days, the watch carries what needs a review, and the agents tab lists the runs asked for lately with who asked (you, or your AI assistant). The verdicts that changed are left to the audit log; the Analytics page is gone, its address leading to the dashboard. Every run's credential now says who asked for it.
  - **Step 13, the top bar as tabs:** the app's name and icon in a row of their own (the icon also the browser tab's), then its pages as tabs (Dashboard, Pipeline, Roles, Companies, Review, Audit log on the left; Profile, Agents, About on the right), each showing it is under the pointer, pressed or selected, folded behind a Menu button on a narrow screen. The About page's parts are tabs (Watching, Finding, Applying, Governance, AI assistant (MCP)), and an application's page links its role's own page and its company's site and careers page, each on one line.

- **4f — Checks through the AI assistant** (noted 2026-11-26, decided 2026-11-27; under way). A check run either by the app's agents, on API credit, or through the operator's own AI assistant over [MCP](mcp.md), on their subscription: a free check first (boards through their APIs, pages opened, no AI), then the pages that need reading handed to the assistant, which saves back what each lists, as evidence; the app's own matching records the verdicts at once, each saying it came from a page the assistant read. The assistant never starts anything that spends API credit. Six steps, notes first.
  - **Step 1, an application's notes and pay expectation:** on the operator's word, with their reason, the assistant adds a note after an application's notes, dated as its own ("Added by your AI assistant, 2026-11-27: …"), never in their place, and sets its pay expectation, replacing the one before (`save_application_notes`, under a new `applications:note` scope held by the assistant alone). Notes that don't begin with the ones before are refused at the write itself, on the record, and an application's stage stays the operator's alone. The Notes tab says so, and when the assistant last added to them; a link to it opens it (a field of the contact form had taken its anchor).
  - **Step 2, a free check:** "Check free" beside "Check all tracked companies" on the Roles page (and every check, Check now too, when no API key is set) calls no AI at all: the worker's `--free` opens a page only the AI could list, leaves it unread and says so (`needs_reading`, nothing billed), names no role from its own page with the AI, and leaves near-misses undecided; boards and pages whose role links are unchanged are read as ever, and their verdicts written. The pages a free check left unread are listed under it, oldest first, until a later check reads them (`verifier:to_read` too); with no key, a company with no careers page is set by hand, since finding one takes the AI. A worker is printed without its API key now (a failing spec had printed one).
  - **Step 3, the assistant reads a page:** `get_pages_to_read` lists the pages a free check left unread, oldest first, with the rules a page is read by, the extractor's own prompt word for word, now in a file both read (`reading_rules.md`; its version unchanged). `read_careers_page` has the verifier's worker open one, free (the worker's new `read` command: rendered as a check renders, robots.txt honored, never the AI), under the verifier's credential naming the assistant as who asked; the page is kept (`page_renders`) for what the assistant saves of it to be checked against, and handed back in parts a chat can hold, its text then its links numbered as the extractor numbers them, fenced as a third-party page's text. The run tools that start the verifier now name the assistant as who asked.
